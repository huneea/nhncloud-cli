# ADR-047: RDS for MySQL 쓰기는 미리보기가 기본이고, `--wait` 는 작업 상태를 성공·실패·불확정으로 나눈다

- **status**: `accepted`
- **결정**: `rds-mysql schema create`, `user create`, `user update`, `user delete` 에 같은 규칙을 둔다.
  - `--yes` 가 없으면 미리보기다. DB 인스턴스와 대상 목록을 조회해 검사하고 보낼 내용을 출력한 뒤 종료 코드 0으로 끝난다. 쓰기 요청은 `--yes` 일 때만 보낸다.
  - 미리보기와 반영 모두 같은 사전 검사를 한다. 같은 이름의 스키마나 같은 `이름@host` 사용자(host 비교는 대소문자 무시)가 있으면, 또는 바꾸거나 지울 `dbUserId` 가 목록에 없으면 종료 코드 3으로 끝난다. 권한이 이미 같으면 `--yes` 를 줘도 요청하지 않는다.
  - 사전 검사는 `dbUserStatus` 를 본다. `user create` 의 중복 검사는 `DELETED` 사용자를 빼고, 같은 사용자가 `DELETING` 이면 삭제가 끝날 때까지 종료 코드 3으로 막는다. `user update` 와 `user delete` 는 대상이 `STABLE` 이 아니면 종료 코드 3으로 막는다.
  - DB 사용자 비밀번호는 `--password-file` 이나 표준 입력으로만 받는다. `--password` 인수는 두지 않는다. 비밀번호는 어떤 출력에도 내지 않는다.
  - `user update` 는 권한(`authorityType`)만 바꾼다. 요청에는 목록 조회로 읽은 현재 `tlsOption` 을 함께 넣고, `authenticationPlugin` 과 비밀번호는 넣지 않는다. 인스턴스 상세의 `supportAuthenticationPlugin` 이 `false` 면 `tlsOption` 도 넣지 않는다.
  - 인증 플러그인 변경은 비밀번호 변경과 함께 콘솔에서 한다. CLI 에는 비밀번호 변경 기능을 두지 않는다.
  - 권한 유형은 `read`, `crud`, `ddl`, `all` 만 받는다. `CUSTOM` 은 받지 않는다.
  - 쓰기 응답은 `jobId` 뿐이다. `--wait` 는 `GET /v3.0/jobs/{jobId}` 를 3초 간격으로 조회한다(기본 상한 300초, `--timeout <sec>`).
    - `COMPLETED` 는 성공(종료 코드 0)이다.
    - `FAILED`, `ERROR`, `CANCELED`, `INTERRUPTED`, `CANNOT_PROGRESS`, `FAIL_TO_READY`, `FAIL_TO_REGISTER` 는 서버가 알린 실패(종료 코드 1)다. 원인을 고쳐 다시 실행하라고 안내한다.
    - `COMPLETED_WITH_ERROR`, `DELETED`, 대기 상한 초과, 상태 조회 실패는 결과 불확정(종료 코드 1)이다. 다시 실행하지 말고 `job get` 과 목록으로 확인하라고 안내한다.
    - 그 밖의 값은 진행 중으로 보고 계속 조회한다.
  - 쓰기 요청이 HTTP 5xx 가 아닌 응답의 봉투 실패로 끝나면 서버가 결과를 알린 실패다. 그 밖의 실패(HTTP 5xx, 시간 초과, 연결 오류, 응답 형식 오류)는 요청이 접수됐는지 모르므로 다시 실행하기 전에 목록으로 확인하라고 stderr 에 안내한다.
- **맥락**:
  - DB 사용자 생성·수정·삭제와 스키마 생성 API 는 모두 `jobId` 만 돌려주는 비동기 작업이다. 응답만으로는 반영 여부를 알 수 없다.
  - 작업 상태 값이 문서 두 곳에서 다르다(12개와 16개). 어느 값이 종료 상태인지, `COMPLETED_WITH_ERROR` 와 `DELETED` 가 무엇을 뜻하는지 문서에 없다.
  - API 가이드의 `dbUserStatus` 는 `STABLE`, `CREATING`, `UPDATING`, `SYNCING`, `DELETING`, `DELETED` 다. 삭제한 사용자가 목록에 `DELETED` 로 남는지, 진행 중인 사용자에게 겹친 요청을 서버가 어떻게 처리하는지는 문서에 없다.
  - 사용자 수정 API 는 네 필드(`dbPassword`, `authorityType`, `authenticationPlugin`, `tlsOption`)가 모두 선택이고, 생략한 필드를 유지하는지 문서에 없다. `host` 와 사용자 이름은 바꿀 수 없다.
  - 콘솔 가이드는 인증 플러그인 변경에 비밀번호 변경을 요구한다. 「사용자 인증에 적용할 플러그인을 변경하려면 반드시 Password를 변경해야 합니다.」, 「Password를 입력하지 않으면 변경되지 않습니다.」 서버가 `authenticationPlugin` 필드가 있는 것만으로 플러그인 변경 경로를 타면, 비밀번호 없는 요청은 거절되거나 인증 문자열 없이 `ALTER USER ... IDENTIFIED WITH <plugin>` 을 실행할 수 있다. TLS 옵션에는 이런 조건이 문서에 없다.
  - 권한 유형은 인스턴스 전체(`*.*`)에 적용된다. 콘솔 가이드의 GRANT 문이 모두 `ON *.*` 이고, 생성·수정 요청에 스키마를 고르는 필드가 없다. `CUSTOM` 은 외부 백업 복원으로 생긴 사용자의 권한을 나타내고, `CUSTOM` 에서 다른 권한으로 바꾸면 되돌릴 수 없다.
  - 공식 문서: [API v3.0 가이드](https://docs.nhncloud.com/ko/Database/RDS%20for%20MySQL/ko/api-guide-v3.0/), [DB 인스턴스 콘솔 가이드](https://docs.nhncloud.com/ko/Database/RDS%20for%20MySQL/ko/db-instance/)의 「DB 스키마 & 사용자」 절.
- **대안 기각**:
  - `--yes` 가 없으면 종료 코드 3([[adr-040]] 의 삭제 방식): 무엇이 바뀔지 보려면 명령을 실패시켜야 한다. 미리보기는 같은 검사를 하면서 쓰지 않는다([[adr-045]] 와 같은 선택).
  - `--password` 인수: 프로세스 목록과 셸 이력에 남는다.
  - `user update` 에 권한만 넣어 보내기: 생략 필드를 기본값으로 덮으면 TLS 설정이 바뀐다. 현재 `tlsOption` 을 함께 보내면 어느 해석이어도 유지된다.
  - `user update` 에 현재 `authenticationPlugin` 도 함께 보내기: 처음에 고른 방식이다. 콘솔 가이드가 플러그인 변경에 비밀번호를 요구하므로, 비밀번호 없이 플러그인 필드를 보내면 권한 변경이 거절되거나 기존 비밀번호로 접속하지 못하게 될 수 있다. 플러그인은 비밀번호 없이 바뀌지 않는다는 문서 문장을 따라 보내지 않는다.
  - `user update` 에 `--auth-plugin` 과 비밀번호 입력 추가: 비밀번호 변경 기능이 새로 생기고 `--authority` 가 선택 옵션이 되어 범위가 커진다. 콘솔이 같은 일을 한다.
  - `dbUserStatus` 를 보지 않는 사전 검사: 삭제가 끝난 기록 때문에 같은 이름의 재생성을 막고, 다른 작업이 진행 중인 사용자에게 수정이나 삭제를 겹쳐 보낸다.
  - 진행 중 사용자에게 경고만 하고 요청하기: 겹친 요청의 서버 처리가 문서에 없어 결과를 예측할 수 없다. 기다렸다가 다시 실행하는 비용이 더 작다.
  - 알 수 없는 작업 상태를 실패로 보기: 문서에 없는 진행 상태 값이 오면 진행 중인 작업을 실패로 알린다. 반대로 성공 목록을 넓히면 실패를 성공으로 숨긴다. 그래서 성공은 `COMPLETED` 하나로 좁히고, 나머지 모르는 값은 상한까지 기다린다.
  - 작업 실패와 결과 불확정에 다른 종료 코드 주기: 종료 코드 0~4 는 모든 서비스가 같은 뜻으로 쓴다(`src/utils/exit-codes.ts`). 한 서비스를 위해 새 코드를 만들면 그 체계가 갈라진다. 두 경우는 stderr 문구와 `--json` 결과의 `applied`, `jobStatus` 로 구분한다.
  - 스키마 이름의 MySQL 예약어 목록 검사: 예약어 목록은 MySQL 버전마다 다르고, API 가이드는 「MySQL 예약어 불가」라고만 적는다. CLI 가 가진 목록이 서버 판정과 어긋나면 만들 수 있는 이름을 막거나 막지 못한다. 예약어는 서버가 거절하게 두고(요청 단계의 봉투 실패인지 작업 실패인지는 실호출로 확인해야 한다), 미리보기는 이를 잡지 못한다고 문서에 적는다.
  - 스키마 단위 권한을 SQL 로 직접 부여하는 명령: CLI 가 DB 에 접속해야 하고, 콘솔이 관리하는 권한 정보와 어긋난다. 필요하면 사용자가 `GRANT ... ON <schema>.*` 를 직접 실행하도록 문서로 안내한다.
- **결과**:
  - 얻는 것: 쓰기 명령을 `--yes` 없이 돌려 대상과 요청 내용을 확인할 수 있다. 결과를 모르는 실패 뒤에 같은 명령을 다시 실행하면 사전 검사가 이미 반영된 생성을 종료 코드 3으로 막는다.
  - 감당할 것: 권한을 스키마 하나로 좁힐 수 없다. 미리보기와 반영이 조회 요청을 두 번 더 보낸다. 사전 검사 뒤 다른 쓰기가 끼어들면 서버 규칙을 따른다. 작업 상태 해석은 실호출로 확인되지 않았고, 다르면 상태 목록만 고친다. 비밀번호 변경, 인증 플러그인 변경, 사용자 정의 권한은 콘솔에서 한다. `authenticationPlugin` 을 생략한 수정 요청이 플러그인을 유지하는지는 실호출로 확인해야 한다.
- **적용 범위**: `rds-mysql` 쓰기 명령. 인증과 endpoint 는 [[adr-046]] 을 따른다.
