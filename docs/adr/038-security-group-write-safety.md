# ADR-038: 보안그룹 쓰기: 이름 기반 인스턴스 연결과 삭제 안전 확인

## 결정

- 인스턴스의 보안그룹 연결 추가·해제는 Compute 서버 액션 `addSecurityGroup`·`removeSecurityGroup`을 쓴다.
  CLI는 입력한 그룹을 UUID로 해석한 뒤, 같은 이름의 그룹이 둘 이상이면 API 요청 전에 입력 오류로 끝낸다.
- 연결 추가는 이미 연결된 그룹이면 요청하지 않고 성공(`unchanged`)으로 끝낸다. 해제는 연결되지 않은 그룹이면 입력 오류로 끝낸다.
  요청 뒤에는 연결 조회로 결과를 다시 확인하고, 반영되지 않았으면 stderr에 경고를 남긴다.
- 보안그룹 삭제는 연결된 포트가 있으면 API 요청 전에 입력 오류로 끝낸다.
  다른 그룹의 규칙이 이 그룹을 원격 그룹으로 참조하면 그 규칙 목록을 stderr 경고로 남기고 삭제를 진행한다.
- 규칙 수정 API가 없으므로 규칙 교체는 `rule delete`와 `rule create`를 차례로 실행하는 비원자적 작업으로 둔다.
- 그룹 삭제, 규칙 삭제, 인스턴스 연결 변경은 TTY 여부와 무관하게 `--yes`를 요구한다.

## 맥락

- 서버 액션은 그룹 ID가 아니라 이름을 받는다.
  실측(2026-09-29, 일반망 kr1)에서 같은 이름의 보안그룹 두 개가 모두 201로 생성됐다. 이름만으로는 대상이 하나로 정해지지 않는다.
- 서버 액션은 대상 그룹만 더하거나 빼므로 인스턴스의 다른 연결을 서버가 보존한다. 인스턴스의 모든 포트에 적용된다.
- 다른 그룹 규칙이 원격 그룹으로 참조하는 그룹을 삭제해도 204로 성공했다. 참조하던 규칙이 사용자 확인 없이 영향을 받을 수 있다.
- 두 동작의 근거는 [Security Groups API](https://docs.nhncloud.com/ko/Network/Security%20Groups/ko/public-api/)와 Compute Instance API의 보안 그룹 추가·삭제 절이다. 공공망 문서도 같은 요청 형식을 정의한다.

## 대안 기각

- 포트 수정(`PUT /v2.0/ports/{id}`의 `security_groups`): 그룹 ID로 지정할 수 있지만 목록 전체를 교체한다.
  읽고 수정해 쓰는 사이에 다른 변경이 들어오면 덮어쓰고, NIC가 여러 개면 포트마다 호출해야 한다.
- 참조 규칙이 있으면 삭제 거부: 공유 그룹 정리 흐름에서 사용자가 참조 규칙을 하나씩 먼저 지워야 한다. 경고로 목록을 남기는 것으로 충분하다고 판단했다.
- TTY 확인 질문: 같은 명령이 터미널과 자동화에서 다르게 동작한다. Load Balancer·API Gateway 쓰기와 같은 `--yes` 필수 방식을 따른다.

## 결과

- 얻는 것: 다른 연결을 보존하는 연결 변경, 대상 그룹 모호성의 사전 차단, 연결 중인 그룹 삭제의 사전 차단.
- 감당할 것: 같은 이름의 그룹이 있는 프로젝트에서는 이름을 먼저 바꿔야 연결을 변경할 수 있다.
  연결 사전 확인과 요청 사이에 다른 변경이 들어오면 사전 판정이 틀릴 수 있다. 사후 확인 경고로만 드러난다.
  규칙 교체 중 삭제만 성공하면 허용 규칙이 빠진 상태가 남는다. 가이드에 새 규칙을 먼저 만들고 옛 규칙을 지우는 순서를 적는다.
